RBAC for the BanyanDB API

A deliberately small authorization layer for every public BanyanDB gRPC and grpc-gateway request—built on the authentication file that operators already deploy.

gRPC · 17912HTTP · 17913Basic AuthNExact Group ScopeDefault OffFail Closed
One policy engine. One method registry. No duplicate HTTP authorization table, external policy server, role inheritance, regex scope, or row-level filtering.

Decision summary

The minimum complete design

When RBAC is enabled, a successfully authenticated username becomes the principal. BanyanDB expands that principal’s scoped role bindings into immutable permission bits and authorizes the semantic gRPC operation before business logic runs.

D-01gRPC is authoritative

Direct gRPC and HTTP gateway traffic pass through the same method policy and evaluator. HTTP does not maintain a second route policy.

D-02Six coarse permissions

schema, data, and cluster, each with the smallest useful action set. Group schemas, property records, and pipelines fold into those areas.

D-03Exact scopes only

A role binding applies to named BanyanDB groups or *. No regular expressions, prefixes, tags, rows, fields, or identity groups.

D-04Atomic security snapshot

Credentials and compiled grants reload as one validated snapshot. Invalid changes retain the last-known-good policy.

Core decision: group scoping is part of phase 1, not a follow-up. It is an acceptance criterion in #13994 and affects query, list, streaming-write, and ByDBQL semantics throughout the implementation.

Scope & goals

Only what #13994 needs

Goals

  • Authorize every externally registered liaison gRPC method and every grpc-gateway request.
  • Bind authenticated usernames and service accounts to built-in or custom roles.
  • Separate read, write, and cluster-level operations.
  • Scope schema and data access to exact BanyanDB groups.
  • Preserve current behavior when RBAC is absent or disabled.
  • Hot-reload policy safely and expose bounded decision metrics.
  • Keep direct OAP/bydbctl clients and the Canopy proxy operational.

Non-goals

  • OAuth2, OIDC, SAML, LDAP, MFA, or token issuance.
  • Row, tag, field, label, time-range, or query-predicate ABAC.
  • Nested roles, role inheritance, explicit deny, or grant delegation.
  • Regex/prefix scopes, one-group-per-tenant assumptions, or identity groups.
  • A policy management API, UI, distributed policy store, or decision cache.
  • Per-browser-user propagation from Canopy to BanyanDB.
  • Authorization of data-node internal listeners unrelated to the public liaison API.

Authorization model

Flat roles, compiled grants

ALLOW iff an authenticated principal has the required permission for every target group.
effective(principal, group) = global[principal] ∪ scoped[principal][group]

Principal

The normalized username established by successful Basic authentication. A service account is simply a dedicated username; no additional principal type is introduced.

Role

A named, flat set of permissions. Roles are configuration conveniences and are expanded during compilation; request evaluation does not traverse a role graph.

Binding

A tuple of principal, role, and exact group names or *. Multiple bindings union their grants. There is no explicit deny.

  • *
Group-name semantics: a binding is attached to a name, not a group UUID. If a group is deleted and later recreated with the same name, the configured grant applies again. A * binding also covers groups created after policy load.

Configuration contract

Extend the file operators already secure

The existing --auth-config-file remains the single source for credentials and RBAC. A separate nested application configuration system or database-backed policy store is not introduced.

users:
  - username: oap
    password: replace-me
  - username: analyst
    password: replace-me-too
  - username: operations
    password: another-secret

rbac:
  enabled: true

  roles:
    monitor:
      permissions:
        - cluster:read

  bindings:
    - principal: oap
      role: writer
      groups: ["*"]

    - principal: analyst
      role: reader
      groups: [sw_metric]

    - principal: operations
      role: admin
      groups: ["*"]

Validation rules

  • rbac.enabled defaults to false.
  • Enabled RBAC requires authentication and at least one user.
  • Duplicate usernames, custom roles, permissions, groups, or equivalent bindings are rejected.
  • Bindings must reference an existing user and role.
  • Built-in role names cannot be overridden.
  • Group names are non-empty exact strings; * cannot be mixed with names.
  • Roles containing cluster:* require a * binding.
  • Unknown RBAC keys and permission names are rejected.
  • The existing owner-only file-mode requirement remains.

Architecture

One decision path for two transports

The HTTP gateway authenticates Basic credentials and forwards them as gRPC metadata. The gRPC authentication interceptor establishes a trusted principal context; authorization never rereads caller-controlled identity metadata.

HTTP :17913
Basic middleware→ grpc-gateway→ gRPC AuthN→ Validate→ RBAC→ Handler
gRPC :17912
gRPC AuthN→ Validate→ RBAC→ Handler

Interceptor order

01Breadcrumb
02Recovery
03Authentication
04Validation
05Authorization

Authentication precedes request validation so malformed unauthenticated calls still receive Unauthenticated. Authorization precedes every business handler invocation.

Unary calls

  1. Load the current immutable security snapshot.
  2. Resolve the full gRPC method to a rule.
  3. Extract and deduplicate every target group.
  4. Require the permission for every group.
  5. Record one decision and invoke or reject the handler.

Streaming writes

  1. Authenticate when the stream opens.
  2. Reject immediately if the principal has no data:write grant anywhere.
  3. Wrap RecvMsg; validate then authorize each resource-bearing frame.
  4. Load the newest snapshot per frame, making revocation effective on the next frame.
  5. Never pass an unauthorized frame to the handler.
Canopy boundary: with the current single upstream Basic credential, BanyanDB authorizes the Canopy service account—not the browser user. Canopy’s local admin/readonly checks remain authoritative for browser sessions. Per-user propagation requires a separately designed signed delegation mechanism and is not part of #13994.

Special request paths

ByDBQL

Parse, bind, and transform first; authorize the resulting native request groups before invoking the native service handler. Raw query text is not the authorization resource.

Group.List

Require at least one schema:read grant, then filter the returned groups to exact visible scopes. A wildcard reader sees all groups.

Multi-group query

Use all-or-nothing semantics. If one requested group is unauthorized, reject the entire query; never silently run an authorized subset.

Runtime operations

Fail closed without becoming brittle

Atomic load and reload

01 · Readowner-only YAML
02 · Parsecredentials + RBAC
03 · Validateall references
04 · Compileimmutable maps
05 · Swapone atomic pointer
  • Credentials and authorization grants are published together as one SecuritySnapshot; callers never observe a new user with an old policy or the reverse.
  • A reload error is logged without secrets, increments a bounded failure metric, and leaves the previous snapshot active.
  • Unary calls use the snapshot selected at the authorization point. Existing streaming writes reload the current snapshot for each frame.
  • Removing a user or binding revokes the next unary call and the next received stream frame. There is no TTL decision cache.

Metrics and audit context

  reason="granted|no_binding|wrong_scope|..."

banyandb_rbac_policy_reload_total{result="success|failure"}
banyandb_rbac_policy_revision 17

Metric labels are bounded by compiled enums and the registered API surface. Username, role name, password, group name, query text, and resource name are forbidden metric labels. Optional structured decision logs may include principal, groups, policy revision, method, and decision, but never credentials or full request bodies.

Unary calls record one decision. Streaming write frames record one decision per resource-bearing frame. An HTTP gateway call is counted only by the gRPC authorizer, preventing double observations.

Compiled representation

type Grants struct {
  Global PermissionBits
  Groups map[string]PermissionBits
}

type SecuritySnapshot struct {
  Revision uint64
  Users CredentialIndex
  Grants map[string]Grants
}

Roles disappear from the request hot path. A scoped decision is two map lookups and a bit test. Global methods consult only Global.

Security behavior, not just code paths

The test plan uses narrow unit tests for policy logic, real in-process liaison integration tests for the complete API contract, and containerized end-to-end tests for direct transports, reload, and cluster behavior. Every denied mutation is followed by a side-effect check.

Resource fixture

  • Groups: rbac-alpha and rbac-beta.
  • Equivalent stream, measure, trace, property, TopN, and registry schemas in each group.
  • Data rows contain group-unique marker values to make leakage observable.
  • Admin creates fixtures before role assertions.
  • Each mutation uses a unique resource ID and verifies persistence or absence afterward.
  • Tests never depend on execution order and clean up their own resources.

Assertions common to every layer

  • Authentication failures are distinct from authorization failures.
  • A denied call does not invoke the target handler or mutate storage.
  • Authorization is evaluated before resource existence is disclosed.
  • Both allow and deny are asserted; success-only tests are insufficient.
  • HTTP and direct gRPC produce equivalent semantic decisions.
  • Passwords, raw authorization headers, and request bodies never appear in errors, logs, or metric labels.
