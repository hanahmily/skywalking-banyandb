# P1 directory-list and CASE capacity verification

This package investigates Q1/A14 on PR #1447 head
`efc0c18988ecbc18a10ffbdd49c7491299d8c8e7`. The original investigation changed no
production code. The subsequent membership fixes and their same-query comparison
are recorded separately in [improvement-results.md](improvement-results.md);
[memory-diagnosis.md](memory-diagnosis.md) explains the rejection boundary and
pooled heap retention. All phases use the real BydbQL Query RPC; schema creation
and writes use normal RPCs.

The [series-scan follow-up](series-results.md) adds proven local count reordering
and actual decoded-buffer reuse without raising limits. Both topologies pass all
48 P1 calls and 568 compatibility specs each; 10,000 timed RPCs complete. The
report preserves memory tradeoffs, timing uncertainty and the cancellation-check
correction. Earlier reports remain historical evidence.

`qlgen/capacity_fixture.go` defines `qlperf.activity`: unindexed scalar
`storage-only.entity_id` is the entity key; scalar `searchable.service_id` has
one keyword inverted index. Integer fields are `value`, `summation`, `count`.
Two shards, zero replicas and no explicit sharding key preserve ordinary routing.
The deterministic fixture has 1,024 services × five entities × two timestamps:
10,240 rows, 4,096 active distinct entities, 8,192 positive rows. Four entities
per service have value one; one is idle. Indexed readiness pages check every
service's five distinct entities, ten rows and sums, then four active distinct
entities and eight positive rows. Distributed traces assert two distinct worker
addresses and exactly 320 source rows per page; value filtering follows native
service selection. Fixture/schema/group/index identity is hashed.

The generated `QL-P1` cohort is explicitly opt-in with `P1_VERIFY=1`; it does
not turn known capacity failures into success expectations or break the default
integration cohort. Four specs contain IN/NOT IN list lengths 10/1,000/10,000,
seven/zero present and duplicate witnesses, empty arrays and NULL, a nonempty
rebind after those empty contracts, plus two-
and sixteen-branch CASE normal/swapped/overlap bindings. Each runs with the plan
cache enabled and bypassed. An admission rejection is recorded and the remaining
bindings are attempted; the qualification spec fails at its end. A wrong result
fails immediately. Expected counts are independent of database queries.

The experiment QL is generated by `P1ListQuery` and `P1CaseQuery`:

```sql
SELECT COUNT(DISTINCT entity_id) AS n
FROM qlperf.activity
WHERE time >= ? AND time < ? AND value::FIELD > 0 AND service_id IN (?)
```

NOT IN changes only the membership operator. Timestamp parameters are native
protobuf timestamps followed by a string array. Two fixed timed cohorts alternate
equally: present-0000 through present-0007,
and present-0008 through present-0015. Each corresponding cohort contains the
same eight present services at every list size, with disjoint absent-ID padding:
IN gives 32; NOT IN gives 4,064. Admitted IN arms read 80 native input rows
per RPC in both cohorts. Correctness-only seven/zero present lists give 28/0
for IN; duplicates
do not multiply results. Empty typed IN is false and empty NOT IN is true;
a nonempty NULL-only list yields UNKNOWN, so neither predicate selects rows.
These expectations follow `docs/interacting/bydbql.md` sections 5.9/5.10.

```sql
SELECT CASE
         WHEN service_id IN (?) THEN 'group-a'
         WHEN service_id IN (?) THEN 'group-b'
         ELSE 'unassigned'
       END AS category, COUNT(DISTINCT entity_id) AS n
FROM qlperf.activity
WHERE time >= ? AND time < ? AND value::FIELD > 0
GROUP BY 1 ORDER BY category ASC
```

CASE binds memberships before timestamps. There are 10,000 total IDs: the first
256 present services map to group-a (1,024), the remaining 768 to group-b (3,072).
Swap reverses counts. One overlapping service yields 1,028/3,068 by first match.
Fourteen additional nonmatching branches preserve the same total IDs/results.

Prerequisites are Linux with Docker, Go 1.26.10, the repository's normal native
build dependencies, and the existing image shown below. Put that Go toolchain on
PATH and use `GOTOOLCHAIN=local`; select writable Go module/build caches if needed.
The image must be present locally. Its exact ID is recorded rather than fetched
or relabeled. `/tmp/pr4-env.sh` below is this machine's toolchain/cache setup;
on another machine replace that line with the corresponding Go environment.

Build once, then run topologies and phases sequentially:

```sh
source /tmp/pr4-env.sh
python3 verification/qlcapacitybench/run.py build --output /tmp/ql-p1-campaign
python3 verification/qlcapacitybench/run.py correctness --output /tmp/ql-p1-campaign
python3 verification/qlcapacitybench/run.py feasibility --output /tmp/ql-p1-campaign
python3 verification/qlcapacitybench/run.py measure --output /tmp/ql-p1-campaign
python3 verification/qlcapacitybench/run.py memory --output /tmp/ql-p1-campaign
```

The runner rejects changed revision/source/binaries/toolchain/image. Its image
is the existing `banyandb-distributed-querybench:go1.26.10`; the manifest freezes
its actual ID. Standalone gets two CPUs/four GiB, distributed four CPUs/eight
GiB; memory-swap equals memory (no extra swap). Go's GOMAXPROCS matches the quota.
Existing integration suites start their existing baseline and vectorized clusters
in one process. The vectorized integration fixture explicitly supplies a four-GiB
process protector; the focused standalone benchmark uses the default cgroup-derived
75% allowance (three GiB). Neither is the 256-MiB vectorized query tracker.
Native protector query pool is allowance/4 and per-query maximum is pool/8:
128 MiB for integration's four-GiB allowance, 96 MiB for benchmark's three GiB.
Actual cgroups, CPU throttling, image/binary/source digests and host load are saved.
CPU affinity is not exclusive host ownership.

Feasibility makes two alternating-binding requests per arm, verifies every
admitted result and checks rejection cleanup and same-cluster small-IN recovery.
A stable rejection is not retimed. Admitted arms receive five fresh process
rounds, rotating full arm order, 20 warmups and 200 timed successful RPCs each.
Two separate equal-work calls verify cache hits or bypass compiles with changed
bindings. The generated cohort independently checks changed answers 32/28/0 and
CASE swapped counts under both cache modes; these are complementary checks.
Every timed result has identical checking. Rejections never enter latency data.
There is no percentage pass gate or adaptive extension. No builds/tests run
during timing. Raw observations retain all samples, byte counts and digests.

An isolated memory process warms each admitted arm before its idle/post-GC
baseline, asserts zero live query/scan ownership, resets query peak, executes one
request, then asserts cleanup. It records allocation/GC/retained heap separately
from timing, per-request cumulative lease-charge deltas, cache counters and named
pool references. `ScanResourceSnapshot().Idle()` covers native cursor references,
owner pins, result leases, decode tasks and scan reservations; long-lived workers
are expected. The native protector's private reservation counter is not exported;
cleanup plus same-cluster recovery provides evidence, not direct observation of
that counter. All memory/CPU/allocation values include client, server and background
work in this process. Retained heap is not attributed to an individual operator.
The separate eight-caller probe defaults to admitted IN 10,000, outside latency timing;
its peak is a process aggregate across concurrent calls. It checks all answers,
rejections, cleanup and subsequent small-IN recovery.
The cancellation probe waits for a native leaf call on admitted IN 10,000 before
canceling and checks recovery; a request that finishes first is reported as such.
`run.py memory --probe-arm case_16` selects the admitted CASE workload for both
cancellation and concurrency; `P1_PROBE_ARM` is the equivalent direct-binary
setting. Ownership checks require a 20-ms quiet interval after client completion
and record the checked memory snapshot, preventing transient cancellation cleanup
from being mistaken for a final idle sample.

See [results.md](results.md) and [results/](results/) for the executed campaign,
capacity qualification failures and remaining unknowns.

For the membership comparison, preserve the original binaries and build the
candidate in a different directory. Run candidate correctness and feasibility,
then compare only the four arms admitted by both versions:

```sh
python3 verification/qlcapacitybench/compare.py run \
  --baseline /tmp/ql-p1-final --candidate /tmp/ql-p1-fixed \
  --output /tmp/ql-p1-comparison
```

This runs five pairs of fresh processes, alternating baseline/candidate order.
Each process uses the same arm order, 20 warmups and 200 successful timed RPCs
per arm. It checks equal request/result digests, request bytes and source-row
counts before reporting differences. It never overwrites the original campaign,
changes budgets or expands the timed workload to rejected queries.
